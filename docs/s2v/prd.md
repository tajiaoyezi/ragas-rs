# /s2v-prd — 交互式 PRD 生成器

> 用产品经理方法论把"我想做 X"翻译成可评审、可归档、可作为 S2V 后续流程输入的结构化 PRD，落盘到 `docs/prds/<kebab-name>.prd.md`。
>
> **设计目标**：产出一份**有信息密度**的 PRD —— 痛点驱动、要证据、范围收敛、边界明确、决策 / 风险 / 开放问题可追踪。完整阈值见各步 GATE 与错误处理表。

---

## 角色定位

执行本流程的 agent 扮演**资深产品经理**，遵循以下心法：

- **从痛点出发，不是从功能出发**。"我们没有 X" 不是问题，"用户因为 Y 流失" 才是
- **要证据，不要直觉**。说"用户喜欢" → 反问"哪些数据 / 谁说的 / 什么场景"
- **承认不知道**。信息缺失就写 `TBD - 需调研`，绝不编造看似合理的需求
- **拒绝填充式写作**。每段必须有信息密度；空话（提升体验 / 优化效率 / 赋能用户）一律拒绝

**反模式（写 PRD 时主动避免）**：

| 反模式 | 正确写法 |
|---|---|
| "提升用户体验" | "首屏渲染从 1.2s 降到 < 500ms（lighthouse）" |
| "优化性能" | "P99 接口延迟从 800ms 降到 < 200ms" |
| "用户应该会喜欢..." | "30 个目标用户访谈中，22 人提到这个痛点" |
| "什么都做"的核心能力清单 | ≤ 5 条核心能力 + 明确 Out of Scope |
| 把方案当问题 | 痛点是"客服响应慢导致流失"，不是"我们没有 AI" |

**TBD 政策**（仅适用于"问答字段"）：

- **适用范围**：步 2-4 的 15 个问答字段（基础五问 + 上下文三问 + 技术轮廓七问）
- **用户主动声明 TBD 视为已响应**：agent 标 `TBD - 需调研`，不再追问该字段
- **不可 TBD 的核心问答**：Q1（谁）/ Q2（痛点）/ Q9（项目类型）—— 这三个字段 TBD 等于 PRD 失去信息密度，agent 必须追问到非空
- **总 TBD 比例 ≤ 50%**：即 15 个问答字段中 ≤ 7 个标 TBD
- **agent 不得替用户填 TBD**：禁止用"看似合理的推测"填空；不知道就标 TBD

**结构化产物（步 5 / 6 / 7）不走 TBD 政策**：

- 步 5 的范围 / 指标 / 阶段拆分、步 6 的决策、步 7 的风险与开放问题，由各自 GATE 阈值（数量 / 类目覆盖）直接校验
- 不进 TBD 比例分母，也不适用"不可 TBD"清单

## 何时用

- ✅ 新项目想用 S2V，但**还没有 PRD**
- ✅ 项目已有 PRD，要为**新功能 / v2 演化**写一份新的（多 PRD 共存，互不影响）
- ✅ 旧 PRD 已过时，想覆写其中某一个（步 0 标记要替换的 PRD，步 8 落盘前才归档）
- ✅ 已初始化 S2V 项目要写新功能 / v2 PRD（不是小修；adapter 已存在）也可走本流程：步 0 会展示 adapter 提示并 GATE 等用户确认；本流程仅生成 PRD 文件，不重新初始化或修改 adapter
- ❌ 单文件实验脚本（不需要 PRD，也用不上 S2V）
- ❌ 未初始化 S2V 项目中的普通 Bug fix / typo 修复
- ❌ 已初始化 S2V 项目中的小修（这类直接走 `/s2v-add task` 即可）

> 多 PRD 共存：一个项目可以在 `docs/prds/` 下并存多份 PRD（v1 / v2 / 各功能各自的 PRD）。`/s2v-prd` 只负责生成 PRD 文件本身，不决定后续工作流——这些 PRD 怎么被消费（接 `/s2v-init`，还是用 `/s2v-add` 逐项补增量产物）由当前项目状态决定，详见本文末尾"与其他流程入口的关系"及 SKILL.md 的"项目识别流程"。

## 执行流程（步 0 → 9，严格按顺序，每个 GATE 必等用户回复）

> **步骤速查**（线性顺读执行；按步名定位，不设行号锚点以免编辑漂移 —— 行号锚点仅 `full-standard.md` §0 因 grep 查阅需要而保留）：
> 步 0 环境校验+多 PRD 路由 · 步 1 理解基础需求 · 步 2 基础五问 · 步 3 上下文补充三问 · 步 4 技术轮廓 7 问 · 步 5 范围/指标/阶段拆分 · 步 6 决策日志(≥3 项) · 步 7 风险与开放问题 · 步 8 渲染 PRD 到磁盘 · 步 9 完工总结
> 流程后参考段：错误处理 · 与其他流程入口的关系 · 实施 agent 的硬约束

### 步 0：环境校验 + 多 PRD 路由

执行意图（按当前环境自适应实现，不要求逐字运行 shell 片段）：

0. 检查 `docs/s2v-adapter.md` 是否存在（adapter-aware 提示，与 SKILL.md "项目识别流程"语义对齐）：
   - 不存在 → 项目尚未初始化 S2V，正常进入下一步
   - 存在 → 项目已初始化 S2V。**展示提示并 GATE 等用户回复**：
     ```
     检测到项目已初始化 S2V（adapter 已存在）。本流程仅生成 PRD 文件本身，
     不会重新初始化或修改 adapter；后续一般走 /s2v-add 追加 phase / task / ADR / feature
     （/s2v-init 仅用于无 adapter 的新初始化项目，已初始化项目跑 /s2v-init 会被直接拒绝）。
     是否继续生成新 PRD？(y/n)
     ```
     ⛔ **GATE**（adapter 存在时）：等用户回复 y/n。
     - `y` → 进入下一步
     - `n` → 结束本流程；建议改走 `/s2v-add` 在已初始化项目里追加 phase / task / ADR / feature（参见 SKILL.md "项目识别流程"）
1. 检查 `docs/prds/` 是否存在：
   - 不存在 → 视为"无现有 PRD"，直接进入步 1（不创建目录；落盘时再 mkdir）
   - 存在 → 列出 `docs/prds/*.prd.md`，排除 `docs/prds/.archive/` 下的文件
2. 若列出为空（目录存在但无 PRD），直接进入步 1。
3. 若已有 PRD，展示文件列表并让用户三选一：
   - **A：写新 PRD**，用于新功能 / v2 演化，与现有 PRD 共存；继续走步 1-9，步 8 按 A 路径同名 GATE 校验（目标同名时可改名或 `archive` 现有 PRD 后继续使用原名）。
   - **B：覆写其中某一个**，用于旧 PRD 已过时、需要替换；用户给出要替换的文件名后，先标记要替换的 PRD（归档动作延后到步 8 落盘前执行），再继续走步 1-9，新 PRD 可用原名。
   - **C：退出**：用户明确不想再生成 PRD（已有的够用 / 走错命令 / 想先用现有 PRD），结束本流程，由用户自行选择后续路径（参见 SKILL.md 的项目识别流程）。

⛔ **GATE**：已有 PRD 时等用户回复 a/b/c，再进入对应分支。

**分支处理**：

- **A（写新 PRD）**：直接进步 1。**步 8 落盘前必须校验** `docs/prds/<kebab-name>.prd.md` 不存在；同名则按步 8 A 路径同名 GATE 处理（改名 or `archive`，详见步 8）
- **B（覆写）**：让用户从步 0 展示的现有 PRD 列表里指定要替换的文件。**输入硬校验**（agent 必须执行，避免任意路径 `mv`）：
  - `<file>` 必须是 `docs/prds/*.prd.md` 直系子文件的精确 basename（如 `login.prd.md`）
  - **拒绝**：`.archive/` 下的文件 / 包含 `..` 或 `/` 的路径 / 绝对路径 / 任意相对路径
  - **拒绝**：不在步 0 展示列表中的输入（即使形式合法 — 防手滑拼错）
  - 不合法 → 重新展示列表让用户改，重试直到合法

  **归档动作延后到步 8 落盘前一刻才执行**（避免用户中途取消时留下半成品状态）。本步只做两件事：
  1. agent 内部记录 `marked_replacement_basename = <basename>`（仅记 basename 不含路径，步 8 落盘前会消费这个标记）
  2. 立即继续走步 1-9，新 PRD 可以与被替换的文件同名（步 8 校验时被标记替换的文件不算占用，但仅当目标 basename 与 `marked_replacement_basename` 一致时——若步 1 改名后目标撞到另一个未确认的 PRD，步 8 GATE 只允许改新名，不接受 `archive` 选项；详见步 8 路径分支）

  归档与新 PRD 写入在步 8 作为连续执行流程一并完成（中间无 GATE 或用户交互打断；OS 层面非原子，但流程语义连续），详见步 8"落盘前确保目录"段。
- **C（退出）**：直接结束本流程，由用户自行选择后续路径（参见 SKILL.md 的项目识别流程）

### 步 1：理解基础需求

**情况 A — 用户在流程入口参数或本轮请求中给了一句话**：

agent 复述理解：

```
我理解你想做的是：
  <复述用户输入，加上 agent 自己的轮廓化补充>

这个理解对吗？需要我调整哪里？
（如果你想顺带给 ASCII slug 名字或版本号，可一并说出，例如 "slug 用 md-toc"、"版本 v2.0"）
（也可以直接确认，回复"是的"或"对"即可继续）
```

**情况 B — 用户没有提供初始需求描述**：

agent 开问：

```
你想做什么？请用 1-3 句话描述这个产品 / 功能 / 能力。

举例（不必参考，只示意粒度）：
  - "给团队做一个内部 markdown 转目录的 CLI 工具"
  - "做一个 Web 应用，让用户可以上传 PDF 自动生成思维导图"
  - "重构现有支付模块，从单体拆出独立 service"

如果你已有 ASCII slug 名字或版本号，可一并说出，例如：
  - "做一个名为 md-toc 的 CLI 工具"
  - "为 my-app 写 v2.0 PRD"
```

⛔ **GATE**：等用户回复。回复含糊 → 追问到能写一句话需求陈述。

**含糊判断标准**（agent 内部检查，不直接告诉用户）：

回复同时包含以下三者中的至少两者 → 通过：

- **场景 / 类型**：CLI / Web / API / 内部工具 / 库 / Mobile / Desktop / ...
- **角色 / 用户**：开发者 / 内部团队 / 终端用户 / 运维 / ...
- **输出物 / 行为**：转换 / 生成 / 重构 / 监控 / 协作 / 同步 / ...

例：

- ×"做点 AI 工具" — 三者都缺 → 追问
- √"做一个把 PDF 转成思维导图的 Web 应用" — 含类型(Web) + 输出物(思维导图) → 通过
- √"给团队做一个内部 markdown 转目录的 CLI 工具" — 含类型(CLI) + 角色(团队) + 输出物(目录) → 通过

### 步 2：基础五问（一次性问，按 TBD 政策处理空缺）

```
为了写出有信息密度的 PRD，请回答以下 5 个问题。可以一起答，越具体越好：

1. 【谁】 这个产品 / 功能服务于谁？
   不要写"用户"——具体到职业、角色、团队规模、使用场景。
   例：×"开发者"  √"3-10 人前端团队的 tech lead"

2. 【痛点】 他们今天具体痛在哪里？
   要写"能观察到的痛苦"，不是"我假设的需求"。
   例：×"缺少协作工具"  √"每周花 2 小时手工合并多人写的设计稿，60% 时间在解冲突"

3. 【现状】 他们现在怎么应对？为什么这些方案不够？
   列出 ≥ 1 个现存方案 + 为什么它们没解决问题。

4. 【时机】 为什么是现在做？
   什么变化让这件事现在值得做？（技术成熟 / 政策变化 / 竞品空白 / 团队学习）

5. 【成功】 三个月后看什么数据 / 反馈，能告诉你做对了？
   尽量给硬指标，不给硬指标也要给可观察信号。
```

⛔ **GATE**：等齐 5 个问题的回答（含 TBD，按 §角色定位"TBD 政策"判定）。

**质量门槛**：
- 任一回答含糊（"用户都需要"/"提升效率"/"看情况"）→ 追问具体
- 核心字段（Q1 谁 / Q2 痛点）不得 TBD → 必须追问到非空
- 其他字段允许 TBD，但需用户主动声明，不得 agent 替填

### 步 3：上下文补充三问

```
基础理解 OK。再来 3 个问题：

6. 【竞品】 市面上有什么解决这个问题的产品 / 工具 / 库？
   （在用户需要且环境允许时，agent 可主动搜索；同时要求用户列出他们知道的）

7. 【差异】 你比它们好在哪？这个差异是关键的吗？
   "差异是关键的"指：用户会因为这个差异选你而不是竞品。

8. 【反对者】 谁可能不喜欢这个产品 / 这个改动？为什么？
   答不出反对者通常说明思考不够深 — 任何东西都会有人不爽。
```

⛔ **GATE**：等齐 3 个回答再继续。

> 第 8 题是"魔鬼代言人"问题。如果用户答"没人会反对"，agent 应主动质疑（如"这会增加构建依赖体积，对极简主义者不友好" / "需要后台服务，有数据隐私顾虑"等）来诱发更真实的回答。

### 步 4：技术轮廓 7 问

```
开始勾勒技术方案。回答以下问题（不知道的写"TBD - 需调研"；Q9 项目类型必填，不得 TBD）：

9.  【项目类型】 CLI / Web / API / Mobile / Desktop / Data Pipeline / Infrastructure / Library / 其他？
10. 【技术栈倾向】 偏好或硬约束（如"必须 Python 3.10+"/"团队只熟 TS"）
11. 【目标平台】 macOS / Linux / Windows / Web / iOS / Android / 跨平台？
12. 【性能要求】 有硬指标吗？（如"启动 < 500ms"/"P99 < 200ms"/"内存 < 100MB"）
13. 【安全 / 合规】 处理敏感数据吗？需要符合什么标准？（GDPR / HIPAA / SOC2 / 等保）
14. 【兼容性】 要兼容旧版本 / 旧 API / 旧数据格式吗？范围多大？
15. 【发布方式】 怎么分发？（npm / PyPI / Cargo / Homebrew / Docker / 内部 CI / 公网 SaaS / App Store）
```

⛔ **GATE（双条件，全部满足才进入步 5）**：

**条件 1 — 等齐 7 个回答**：Q9 为 TBD → 拒绝继续，追问到非空。

**条件 2 — TBD 复核通过**（条件 1 通过后立即执行）：

- 统计步 2-4 的 15 个问答字段：`answered=<N>` · `TBD=<K>` · `TBD%=<K/15>`
- 核心问答 Q1（谁）/ Q2（痛点）/ Q9（项目类型）任一 TBD → 回退到对应字段追问
- `TBD% > 50%` → 提示用户："当前 TBD 比例 <X>%，超过 50% 阈值，请补足以下字段：<列出 TBD 字段名>"，回到对应字段追问
- 通过 → 在对话回复里展示统计结果（一行即可：`📊 信息密度：answered=N · TBD=K · TBD%=X%`），进入步 5

### 步 5：范围、指标与阶段拆分

先确认 PRD 模板中会直接落盘的产品范围与指标，避免 agent 仅凭推断填充关键章节：

```
在拆 phase 前，请先确认以下内容。可以接受我的初稿，也可以直接修改：

1. 【核心能力】1-5 项，每项一句话说明"做什么 + 一个具体例子"。
2. 【明确不做】至少 3 项，用来收住边界。
3. 【关键模块】≥ 3 个，每个一句话职责。下游 `/s2v-init` 渲染 phase spec 的"涉及模块"列时会用到。
   例：×"前端 + 后端"  √"parser.ts: 解析 markdown 标题 / slugger.ts: 生成 URL-safe id / index.ts: 协调主流程"
4. 【用户流程】主流程 1 条、异常流至少 2 项、边界场景至少 1 项。
5. 【成功指标】主要指标至少 1 个，次要指标至少 2 个，反指标至少 1 个。

我会基于前面回答给一版初稿，你确认后再进入阶段拆分。
```

agent 给范围与指标初稿 → 用户审。

⛔ **GATE**：等用户确认。核心能力 < 1 或 > 5、明确不做 < 3、关键模块 < 3、主流程为空、异常流 < 2、边界场景 < 1、主要指标 < 1、次要指标 < 2、反指标 < 1 → 拒绝继续，回本段起头，重新确认范围与指标。

范围与指标确认后，再拆 phase：

```
我们一起把工作拆成 N 个 phase。原则：

- 每个 phase 是一个**可验证的里程碑**（不是"开发到一半"）
- 阶段越靠前越独立；后阶段可依赖前阶段产物
- 标出**可并行的阶段**（多人协作时关键）
- 每个 phase ≤ 1-2 周工作量；超出就再拆

我来给一个初稿，你审一下：
```

agent 基于步 1-4 收集的信息，以及本步已确认的范围与指标，主动给一份阶段表初稿（Markdown 表格），结构如下：

```markdown
| # | Phase 名称（kebab）| 描述（完成后能做什么）| 范围（涉及模块 / 文件）| 依赖 | 可并行 |
|---|---|---|---|---|---|
| 1 | foundation | <一句话：解锁了什么能力> | <module-1> + <module-2> | - | 否（基础设施）|
| 2 | <name> | <...> | <module-3> | 1 | 是（可与 phase 3 并行）|
| 3 | <name> | <...> | <module-4> | 1 | 是（可与 phase 2 并行）|
| 4 | integration | <端到端跑通什么> | <module-5> + 集成测试 | 2, 3 | 否 |
```

然后向用户：

```
请审这份阶段表，告诉我：
- 接受 → "ok" 或 "可以"
- 改某行 → "把 phase 2 改成 X"
- 加 / 减 phase → 直接说
- 整个推翻重来 → "重拆"，然后我会问更细的问题
```

1. 从步 1 用户输入推断 `kebab-name`（按下方"kebab-name 推断规则"严格执行；用户显式给名字时优先用用户给的，但仍需通过校验）。

- **B-match 子分支不触发此 GATE**。

**kebab-name 推断规则**（agent 不得自由发挥；同一输入在不同 agent 间需产出同一结果）：

1. 用户在步 1 显式给名字 → 跳过下面第 2/3 步推断，但**仍需走第 4 步产物校验**：必须是合法 ASCII kebab-name（仅小写字母 / 数字 / `-`，长度 ≤ 30，不能为空 / 不能以数字开头 / 不能纯数字）；不合法 → 提示用户改

   b. 空格 / 下划线 / 点 → 单个 `-`

**落盘前确保目录与归档**（agent 自动；执行到这一步说明所有 GATE 已过、**版本号已派生完成**、即将真正写文件。归档与新 PRD 写入是连续执行流程，中间无 GATE 或用户交互打断；OS 层面非原子操作，若中间步骤失败需向用户报错并保留现场，避免半成品入库）：

## 错误处理

| 场景 | 行为 |
|---|---|
| `docs/s2v-adapter.md` 已存在（项目已初始化 S2V） | 步 0 GATE 等用户回复 y/n；`y` 继续走步 0 后续 / `n` 直接结束本流程，建议用户走 `/s2v-add`（详见步 0） |
| `docs/prds/` 已有 PRD | 步 0 三选一路由：a 写新 PRD（共存）/ b 覆写其中某个（先标记，步 8 归档）/ c 退出本流程，由用户按当前项目状态选择后续路径（详见步 0） |
| 步 8 推断的 kebab-name 与现有 PRD 同名 | A 路径 / 目录从空开始：等用户给新 kebab-name 或回复 `archive` 归档现有的；B-mismatch：**只能改新名**（不接受 `archive`，避免双归档语义）；详见步 8 落盘前校验 |
| 步 8 解析原 PRD 版本号失败（B 路径非 semver） | 落盘前校验段步骤 5 触发 GATE：展示原版本号 + 等用户给新版本号（匹配 `^v\d+\.\d+(\.\d+)?$`）；**必须在 mkdir / mv 前完成**，避免破坏"归档与写入连续无 GATE"硬保障 + 避免 v2 / 2026.05 等版本号被静默降回 v1.0；详见步 8 落盘前校验段步骤 5 + 派生表"版本"行 |
| 用户中途取消 | 不落盘、不创建目录、不归档，对话结束（mkdir 与归档动作均在步 8 落盘前一刻才连续执行；用户在步 1-7 任何 GATE 取消都不会留下半成品：旧 PRD 仍在原位、`.archive/` 不会被创建、`docs/prds/` 不会出现空目录） |
| 步 2 / 3 / 4 用户不肯回答某些问题 | 按 §角色定位"TBD 政策"处理：用户主动声明 TBD 视为已响应；核心字段（谁 / 痛点 / 项目类型）不得 TBD；只统计步 2-4 的 15 个问答字段，总 TBD 比例 > 50% 拒绝落盘；agent 不得替用户填 TBD |
| 步 5 范围与指标未确认，或阶段表少于 1 项 | 拒绝继续；范围与指标未确认时回本段起头，阶段表少于 1 项时重新拆分阶段表；至少确认核心能力 1-5 项、明确不做 ≥ 3 项、关键模块 ≥ 3 个、主流程 1 条、异常流 ≥ 2 项、边界场景 ≥ 1 项、主要指标 ≥ 1 项、次要指标 ≥ 2 项、反指标 ≥ 1 项、阶段表 ≥ 1 项 |
| 步 6 决策少于 3 条 或 类目覆盖少于 3 类 | 拒绝落盘；引导用户从 §16.1 八类（`架构`、`依赖`、`数据持久化`、`协议接口`、`安全`、`测试工具链`、`部署发布`、`兼容性` — 字面以 §16.1 为准）中补足至少 3 条且至少覆盖 3 类（避免"D1=React / D2=Vue / D3=Svelte"这种 3 条但只占 1 类的情况）|
| 步 7 技术风险少于 3 项或开放问题少于 1 项 | 拒绝落盘，回步 7 起头；技术风险不足时，agent 引导用户从依赖锁定 / 性能假设 / 边界条件 / 外部 API 变更 / 第三方服务可用性等通用风险类别中补足至少 3 项；开放问题不足时，引导用户列出至少 1 个待确认事项 |
| 用户在任一 GATE 给空回复 / "随便" | 引导式提问（agent 给 2-3 个选项让用户选）|

## 实施 agent 的硬约束

- ✅ 严格按步号顺序（步 0 → 9）
- ✅ 遇到 ⛔ GATE 必须等用户回复再继续；无 GATE 的环境校验、落盘、总结可连续执行
- ✅ 步 2 / 3 / 4 / 5 / 6 / 7 必须等齐用户回答，不许"agent 替用户填"
- ✅ 信息缺失要标 `TBD - 需调研`；禁止编造看似合理的需求
- ✅ 章节标题严格按"中文｜English"双语格式（`/s2v-init` 解析锚点不可破坏）
- ✅ 步 5 的范围 / 指标 / 阶段表、步 6 决策、步 7 风险与开放问题由 agent 给初稿 → 用户审改 → 用户拒绝时回到对应小节起头
- ❌ 禁止跳过任何 GATE
- ❌ 禁止重命名 PRD 章节标题
- ❌ 禁止把 PRD 落到非 `docs/prds/` 目录
- ❌ 禁止覆盖现有 PRD（步 8 必须做同名校验；A 路径同名时强制用户改名或归档，**B-mismatch 同名时只允许改名**；破坏 SDD 单一事实源即视为违约）
- ❌ 禁止用空话填充（"提升体验" / "优化效率" / "赋能用户"等）
- ❌ 禁止在用户确认前把 agent 推断的 trade-off 写成最终决策（可以给候选初稿，但必须经 GATE 确认后落盘）
- ❌ 禁止落盘后主动 `git add` / `git commit`（commit 由用户审完后手动执行；避免半成品入库）
- ❌ 本流程只允许创建 / 归档 `docs/prds/*.prd.md` 与 `docs/prds/.archive/*.prd.*.md`，不得顺手修改 `docs/s2v-adapter.md`、`AGENTS.md`、`docs/s2v-snapshot.md` 或其他项目文件
